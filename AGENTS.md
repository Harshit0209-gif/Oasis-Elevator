# Oasis Elevators — project notes

This is a Vite + React 19 + TypeScript single-page app (migrated off Next.js — no SSR, no App Router, no API routes). Routing is client-side via `react-router-dom`.

- `@/*` resolves to the repo root (see `vite.config.ts` / `tsconfig.json`), so `components/`, `data/`, `lib/`, `hooks/` stay at the top level rather than under `src/`.
- `src/` holds the app shell: `main.tsx` (entry), `App.tsx` (routes + layout), `pages/*.tsx` (one per public route), `index.css` (Tailwind v4, CSS-first config), and `src/admin/` (the CMS admin panel — see below).
- Per-page `<title>`/`<meta>` tags are set via `lib/seo.tsx`'s `<Seo>` component, which relies on React 19's native hoisting of `<title>`/`<meta>`/`<link>` rendered anywhere in the tree — no `react-helmet` needed. Per-page title/description are CMS-managed (`seo_settings` table, admin at `/admin/seo`) via the `useSeo()` hook, falling back to a hardcoded default if the CMS hasn't loaded yet or nothing's been set.
- Because this is a static client-rendered SPA, there's no server for the contact form to post to. `ContactForm.tsx` reads an optional `VITE_CONTACT_ENDPOINT` env var; without one set, submissions just validate and show a success state locally. Wire up a real form backend (Formspree, a hosted function, etc.) before relying on this in production. **The contact form is intentionally excluded from the CMS migration below — do not wire it to Supabase.**
- `OfficeMap.tsx` embeds the office location via the Google Maps Embed API, reading the key from an optional `VITE_GOOGLE_MAPS_API_KEY` env var; without one set, it falls back to an address card instead of a broken iframe.
- `npm run build` type-checks (`tsc --noEmit`) then runs `vite build` to `dist/`. `npm run dev` starts the Vite dev server on port 3000.

## Content CMS (Supabase)

Almost all editable content — Hero, About, Why Oasis, Products, Services, Industries, Our Process, Projects, Testimonials, Statistics, Certifications, FAQs, Clients, Navigation, Footer, Settings, SEO, Media — lives in Postgres (Supabase), not in `data/*.ts` files. Public pages fetch it at runtime; nothing is baked into the JS bundle at build time anymore.

- **Schema / RLS / storage**: `supabase/migrations/*.sql`, run once against the project in order (001 → 004) via the Supabase SQL Editor. `001_schema.sql` (tables), `002_rls.sql` (Row Level Security — public reads `status = 'published'` only, admins get full access via an `admin_profiles` role check), `003_storage.sql` (the `media` storage bucket, JPG/PNG/WEBP only — SVG upload is intentionally unsupported, XSS risk without a sanitizer), `004_seed.sql` (the site's real content, ported from the old `data/*.ts` files — testimonials and certifications seed empty, no fake data).
- **Env vars**: `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` (anon/publishable key only — the service role key must never be used client-side; every privileged operation is enforced by Postgres RLS via the signed-in admin's session, not by holding a more powerful key).
- **Public read layer**: `lib/supabase.ts` (client), `lib/content.ts` (typed fetchers, mapped to the same shapes the presentational components already expected — see `data/types.ts` — so components themselves needed minimal changes), `hooks/use-content.ts` (generic fetch-on-mount hook).
- **Admin panel**: `src/admin/`, mounted at `/admin/*` in `App.tsx` via `React.lazy()` so none of it ships in the public bundle. Supabase Auth (email/password) + an `admin_profiles` table gate access — there's no public signup route. Most content types share one generic `CollectionPage` + `CollectionItemForm` (config-driven per module in `src/admin/config/collections.ts`, with drag-to-reorder via `@dnd-kit`) rather than 11 bespoke CRUD UIs; singletons (Hero/About/Footer/Settings/SEO/Navigation) have their own small editor pages.
- **First admin user**: created directly via Supabase Auth + a manual SQL insert into `admin_profiles` (see git history / ask for credentials) — there's no seed script for this since it needs a real `auth.users` row, not just a data row.
- **The "Our Process" elevator animation** (`components/sections/process/ProcessShaft.tsx`) computes everything — floor count, scroll distance, active-floor detection — from `steps.length` at render time. Adding/removing a step in `/admin/process` changes the animation automatically; no code changes needed. Icons for Process Steps, Services and Industries are stored as plain string names (e.g. `"Wrench"`) resolved against a curated allow-list in `lib/resolve-icon.ts` / `components/sections/process/process-icons.ts` — never a dynamic `(LucideIcons as any)[name]` lookup.
- `data/*.ts` files that used to hold this content have been deleted (`data/types.ts`, `data/accessories.ts`, `data/cabin-config.ts` remain — the first for shared type definitions still used by the content-mapping layer, the latter two because they're intentionally still static/out of CMS scope).
